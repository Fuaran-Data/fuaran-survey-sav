# Decisions

## 2026-11-09 — D8: publication is a tag, under Trusted Publishing

A `v*` tag push runs `.github/workflows/publish-packages.yml`: the gate, then `dotnet pack` of the one
project into a repository-local directory, then a push to nuget.org under Trusted Publishing (OIDC) —
the job's token is exchanged for a one-hour API key by a policy registered on nuget.org naming this
repository and this workflow file, so no long-lived secret exists anywhere. A branch push reaches nothing.
The package id is guarded in the workflow: anything but `Fuaran.Survey.Sav.*` refuses the whole push.
The version is `<Version>` in `Directory.Build.props` at the tagged commit; a change to the public surface
advances it in the same commit. Registering the nuget.org policy (owner, repository, workflow file) is the
one per-repository act and is done once, before the first tag.

Design decisions that shaped `Fuaran.Survey.Sav`, newest first, with the reasoning that would have
to change for them to be revisited.

## D7 — Role 1 is named `Target`

PSPP's appendix lists the `$@Role` values as Input, Output, Both, None, Partition, Split. SPSS's
own user interface calls role 1 "Target", and that is what a consumer reading SPSS output expects
to see, so the union case is `Target`. The appendix's name is noted on the type.

## D6 — The display-parameter record is indexed by variable record, segments included

Subtype 11 holds two or three int32s per variable. PSPP's appendix says the entries correspond to
variable records in order, with no entry for the continuation records of strings wider than 8
bytes. The segments of a very long string (> 255 bytes) are ordinary variable records, so each has
its own entry, and the folded variable takes the entry of its first segment. The reader accepts a
record whose count is 2 or 3 times the number of such records and otherwise leaves the measure,
width and alignment unset rather than guess; the raw record is still available.

The fixture generator writes one entry per segment for this reason.

## D5 — A parsed `$@Role` leaves the attribute map

`Variable.Role` carries the role; keeping `$@Role` in `Variable.Attributes` as well would make a
consumer reconcile two statements of one fact. When the attribute's value is not one of 0..5 it is
left in the map untouched, so nothing is lost.

## D4 — The dictionary fingerprint is SHA-256 over the dictionary bytes

`Dictionary.Fingerprint` is the lower-case hex SHA-256 of the file from byte 0 to the end of the
type-999 record: the header and every dictionary record exactly as written. It identifies a
delivery's schema without reading its cases, and the columnar manifest records it so a store can
be matched to its source. It deliberately includes the header, so two files whose dictionaries
differ only in compression or byte order have different fingerprints: they are different byte
streams, and the hash says what it hashes.

## D3 — Fixtures are generated by a committed script, but the gate never runs it

`tests/fixtures/gen_sav.py` writes the eight fixture files and their expected renderings
independently of the reader, from the PSPP appendix. The generated files are committed. The gate
(`run.ps1`) reads them and needs nothing beyond the .NET SDK; `-Regenerate` runs the generator
deliberately, and its result is reviewed as a diff. A gate that depended on Python would add a
toolchain to every consumer's CI for a file that changes a few times a year.

## D2 — The columnar store is a format of this package's own, not Parquet

The store is a directory of little-endian typed column files, validity bitmaps, UTF-8 string tables
and a JSON manifest, written deterministically. A Parquet writer would have made the store readable
by more tools at once, but it would have made the public reader carry a dependency, which D1 rules
out. The layout is small enough to be stated in the README and read back with memory-mapped files
and nothing else; a host that wants Parquet can transcode from it.

## D1 — The repository: public, Apache-2.0, re-homed from FSharpSAV, FSharp.Core only

The reader is ported from `SavLib.fsx` in the author's MIT-licensed FSharpSAV repository. The
copyright holder is the same (Andrew J. Willshire / Diametrical Ltd), so relicensing the port under
Apache-2.0 is the holder's own choice. The port keeps the reading logic and the CSV rendering, which
the byte-for-byte fixture tests depend on, and leaves behind the xlsx writer, the file checker,
the variable browser and the pivot engine, which are tools rather than a reader.

`FSharp.Core` is the only runtime dependency; Expecto is test-only. A reader for a wire format
should cost a consumer nothing but itself.
